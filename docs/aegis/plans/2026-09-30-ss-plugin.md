# Shadowsocks SIP003 plugins + VLESS TCP mux — Implementation Plan

Date: `2026-09-30`
Status: `ready for execution`
Spec: `docs/aegis/specs/2026-09-30-ss-plugin-design.md` (rev. 14, approved)
Scope: `xray-tui-proto`, `xray-tui-native`, `xray-tui-core`, `xray-tui`, docs

## Aegis Visibility

A durable plan because this change rewrites a **frozen identity format**, **wipes the user
database** (schema tag 13 → 14), adds a **new transport owner**, changes a **shipped
protocol's behavior** (VLESS mux framing), and has a **verification boundary no CI can meet**
(a real SIP003 plugin server needs Go binaries). Each of those is expensive to reverse after
code lands.

## Goal

Make real-world Shadowsocks subscription rows that carry a SIP003 plugin connect **natively**,
with named refusals where we cannot, and make VLESS `mux` rows stop being parsed-and-dropped.
Definition of done is the spec's 31-row acceptance matrix; nothing ships while a row in it is
unaccounted for.

## Architecture

```
dial ──▶ [TLS if the plugin's `tls` key says so] ──▶ plugin framing ──▶ [mux if mux_active] ──▶ SS codec
                                    (ws | obfs=http | obfs=tls)      (protocol phase)     (per session)
mode=quic:  quinn dial replaces dial + TLS + framing; the SS codec runs over the QUIC stream
```

Owners, each single and named (spec §3, §5, §5.1, §5.2, §7):

| owner | file | owns |
| --- | --- | --- |
| stored config | `proto/src/proto_spec/ss.rs` | `PluginSpec` — total, lossless, one parse function |
| SNI policy | `proto/src/proto_spec/ss.rs` → `plugin_sni()` | the sing-box three-term rule; two callers |
| framing | `native/src/transport/v2ray/` | ws / obfs=http / obfs=tls bytes on a `BoxStream` |
| mux codec | `native/src/transport/mux/` | the v2ray frame format + session pool (extracted) |
| mux layer | `native/src/protocol/mod.rs` → `connect_mux` | `MuxClient`; the SS arm runs the codec per session |
| dispatch predicate | `proto/src/proto_spec/ss.rs` → `mux_active()` | `resolved_mode.is_stream() && resolved_mux > 0` |
| verdicts | `native/src/capability.rs` | every connect-time refusal, one per key/value |
| runtime verdicts | `native/src/protocol/ss/udp.rs` | the UDP refusal + one `warn!` |

## Compatibility Boundary

- **Breaks:** every stored database is recreated on first launch (`user_version` 13 → 14). All
  profiles, groups, measurements, subscription state. Accepted (decision 4, pre-alpha) and it
  ships **with** Slice 1, never alone.
- **Breaks:** identity uids change for **every** protocol row (the version byte is written
  first).
- **Changes behavior:** VLESS profiles that request mux are sent mux-framed (one session per
  connection, **no connection reuse**). They connected before and still connect.
- **New refusals:** an SS row with a plugin becomes *connectable* where it was refused; a row
  with an unregistered plugin name, an unsupported mode, `cert`/`certRaw`, `obfs=websocket`,
  mixed vocabulary, REALITY, or a smux/yamux VLESS row becomes **refused by name** where it was
  previously silent. Each keeps the `[untestable]` marker and purge safety.
- **Unchanged:** every non-plugin SS row, every non-mux VLESS row, both core injectors'
  output for non-plugin rows, the batch pipeline outside the Slice-5 fix.

## Change Necessity

Docs/config cannot deliver this: the stored `SsConfig` must become lossless and typed, four
option spellings must be parsed, the wire framing is new code in a new module, and the
production mux path is unreachable today. The minimum code boundary is the seven owners above;
nothing else needs to change.

**Existence Check.** `transport/v2ray` (framing on a stream) and `transport/mux` (frame codec +
session pool) are both new and neither has an existing owner: `transport/ws.rs` is protocol
transport, not plugin framing, and `protocol/vless/mux.rs` is a protocol module whose codec is
protocol-independent. `plugin_sni` and `mux_active` are **not** new owners — they live in the
proto crate beside the spec they read, which is the only place that can answer them once.

### Slice 0 — Oracle acquisition (no product code)

**T1 — pinned plugin binaries + a gated recipe.** *(executed 2026-09-30; one half blocked, see
the evidence note)*

- *Purpose:* tier 3b currently has no server. Nothing in Slices 1–3 can be proven without it.
- *Files:* `justfile` (new `plugin-bins` recipe). No product code, no manifest change.
- *Minimum change:* install pinned binaries into `XRAY_TUI_PLUGIN_BIN_DIR`, verify each, and
  fail loudly — the same shape as the `XRAY_TUI_CORE_BIN_DIR` contract, never a CI requirement.
- *Compat:* none. No product path changes.
- *Verify:* the recipe installs and runs what it can; a missing prerequisite names its own
  install command and exits 2.

**Evidence note (2026-09-30) — what the pins actually are, discovered not assumed:**

- `v2ray-plugin` ships a prebuilt `linux-amd64` asset at **v1.3.2**, tarball
  `sha256 b5785142…3ee541a`, containing `v2ray-plugin_linux_amd64` (underscores inside the
  tarball, hyphens in the asset name — both mapped in the recipe). Its own flags confirm the
  spec's §2.2 defaults directly: `-host` defaults to `cloudfront.com`, and it has `-mode`,
  `-mux int`, `-path`, `-tls`. **Installed and verified running.**
- The obfs side is **not** a download. `shadowsocks/simple-obfs` master is **C** (not the Go
  port), and its only published release asset (`v0.0.5/obfs-local.zip`) is **Windows-only**
  (`obfs-local.exe` + `libwinpthread-1.dll`), so there is no Linux binary to fetch. The recipe
  therefore builds the **v0.0.5** tag with autotools; `configure` hard-requires `asciidoc`
  and `xmlto` for the man pages, which the binaries never use, so the recipe stubs those two
  rather than installing two doc toolchains.
- libev (its only dependency) is **not** a prerequisite to install: it has no dependencies
  of its own and builds to a user prefix with no root, so `just plugin-bins` builds it into a
  temp prefix when neither the system nor `$HOME/.local` has one. `simple-obfs` probes
  `-lev`/`ev.h` directly, so no pkg-config is needed — only `CPPFLAGS=-I…`/`LDFLAGS=-L…`.
  Verified: all three binaries build and run here, with no root.
- Useful for the 3b harness design (T8/T12): the C obfs binaries read `SS_REMOTE_HOST`,
  `SS_REMOTE_PORT`, `SS_LOCAL_HOST`, `SS_LOCAL_PORT`, `SS_PLUGIN_OPTIONS`
  (`simple-obfs/src/local.c:889-893`) — the same env contract shadowsocks-rust drives plugins
  with (`shadowsocks/src/plugin/ss_plugin.rs`). Note WHICH binary is named: **`obfs-server`**
  is the server side and binds `SS_REMOTE_PORT` (`src/server.c:1437-1438`); `obfs-local` is
  the client half and binds `SS_LOCAL_PORT` (`src/local.c:913`) — the port `ssserver` already
  holds, hence EADDRINUSE on every fresh port (the pinned cause below). Its **other** plugin style
  (`plugin/obfs_proxy.rs`, `--data-dir … client|server`) is the obsolete `obfsproxy` arg
  convention and must not be used here.

**Slice 1 status (2026-09-30).** T2, T3, T4, T5, T6 and T7 are implemented and green
(`xray-tui-proto` 399, `xray-tui-native` 673, `xray-tui-config`, `xray-tui-core` — all
passing). Two design deltas came out of executing them, both recorded here because the
spec/plan text above still describes the pre-implementation shape:

1. **`PluginMode` grew an `Unsupported(String)` variant**, and family/mode are **normalized
   at parse**. Both were forced by real corpus rows: `obfs=websocket` (the legacy smux
   dialect) was being silently rewritten to `http` — the exact misclassification the
   "never refuse, never guess" rule exists to prevent — and the export elision made a
   default-valued mode unrecoverable, so `uid(parse(u)) != uid(parse(export(parse(u))))`
   for every default-mode row. Normalizing at parse is what makes the fixed point hold.
2. **The read side of `obfs=tls` is record-bounded**, not "discard 3 bytes per read" like
   the reference: a read that crosses a record boundary made the next read eat 3 bytes of
   real payload. The excess is buffered instead. The constants are also hex-spelled
   (`0x16`/`0x17`) because a decimal `17` silently emits `0x11`.

Also recorded by execution: the tier-1b corpus test counts a second, **pre-existing**
parse failure shape — a row whose base64 userinfo is percent-encoded mid-string
(`…J%2BHsw`), which fails at the userinfo layer before any plugin branch. It is counted
and asserted present, not fixed: a userinfo-layer change is a separate concern from
SIP003. T8 therefore needs only the two obfs dials against the real `obfs-local`.

**T8 — slice gate.** 3b rows 1–2 against the real `obfs-server`, then the full baseline

**3b server side, status (2026-09-30).** `just plugin-bins` builds and installs all three

passes the paths to the linker as input files.

**The server-side cause, pinned (it was a wrong binary, not a mystery).** `ssserver` spawns
whatever `--plugin` names (`shadowsocks/src/plugin/mod.rs:238-242`), and in `PluginMode::Server`
the contract is "the plugin listens on `remote_addr`, the SS server takes `local_addr`"
(`mod.rs:72`). Passing **`obfs-local`** — the *client* half — made the plugin bind
`SS_LOCAL_PORT` (`simple-obfs/src/local.c:913`), which `ssserver` had just taken: EADDRINUSE on
every fresh port. The server side is **`obfs-server`**, which binds `server_port` =
`SS_REMOTE_PORT` (`src/server.c:1437-1438`):

```
ssserver -s 127.0.0.1:36666 -m aes-256-gcm -k hunter2 \
  --plugin obfs-server --plugin-opts "obfs=http;obfs-host=cdn.example"
# → plugin: "obfuscating enabled", "listening at 127.0.0.1:36666"
#   ssserver: "listening on 127.0.0.1:46241, inbound address 127.0.0.1:36666"
```

For v2ray-plugin the name is the same in both roles (one binary; the role is an option —
`--plugin-opts "server;obfs=…"`), which is why only the obfs family needed the server
binary. The recipe therefore installs **both** halves, and the harness must pass
`obfs-server` for the server side.

Both modes (`obfs=http`, `obfs=tls`) fetch the echo body over the tunnel. The oracle found
**four real defects**, none of which the hermetic tests could see:

1. `http_obfs` read: `buf.put_slice(&rest)` with an unbounded remainder (226 bytes into a
   32-byte buffer) — `ReadBuf::put_slice` panics, so any small-chunk reader (hyper included)
   would have panicked the connection. Now a `pending` buffer, filled to `buf.remaining()`,
   and a unit test reads 300 bytes through a 32-byte buffer.
2. `tls_obfs` **handshake header order**: we wrote `type, version(2), length(3)`; the C struct
   declares `type, length(3), version(2)` and `check_tls_request` only accepts when the version
   is at `data[9..11]` (`obfs_tls.c:514-520`). On mismatch the plugin `disable`s **silently**
   (`obfs_tls.c:525-530`) and passes our record through raw, which reached ssserver as
   `decrypt length failed`. Caught by the reference's own bytes: the built `obfs-local` emits
   `16 03 01 00 ec | 01 | 00 00 e8 | 03 03 …`.
3. `tls_obfs` read layout: the C server's first buffer is
   `[server_hello 96][CCS 6][encrypted_handshake 5][payload]` with the payload **raw** (no
   `17 03 03` header) and the length at **105** — sizes printed by a C probe over
   `obfs_tls.h` (`sizeof` 96 / 6 / 5, `offsetof(len) = 3`). Those field sums ARE the sizes
   because every one of these structs is declared `__attribute__((packed, aligned(1)))`
   (`obfs_tls.h:47,56,62,85,116,123,130`), so the `short`/`int` members sit on odd offsets
   (`handshake_version` at 9, `random_unix_time` at 11) with **no** padding inserted. Assume
   alignment instead and the arithmetic yields a 100/8/6 triple — a payload at 114, which is
   what a hand-derived reading produced before the probe settled it. The Go port's "discard 105 then
   3 bytes per read" is where the inherited constant came from; the C shape is normative
   because the C `obfs-server` is the oracle. A test pins `FIRST_FLIGHT_SKIP == 105`.
4. **Coalescing: investigated, and it is safe** — an earlier reading of this row claimed the C
   server truncates the buffer to the ticket's payload and would discard records coalesced
   behind the hello. It does not: `deobfs_tls_request` moves the ticket payload to the front
   and preserves what followed (`memmove(buf->data + ticket_len, buf->data + hello_len,
   buf->len - hello_len)`, `obfs_tls.c:424-430`), then deobfuscates the tail as app data
   (`:434-435`). The write path therefore stays **per write** (first write → hello, later
   writes → records), which is the reference shape and bounds the buffer; row 2 passes with it.

## T27 FINAL GATE (2026-10-01) — and a false green I nearly shipped.

The gate is now run over `--workspace`, not over a list of crates I happened to touch, and that
change is the most important thing in this section.

### The false green

Every per-crate clippy run in this plan reported `0` for `xray-tui` and `xray-tui-db`. **Both were
false.** `cargo clippy -p <crate> --all-targets` could not COMPILE — the crates still carried

the same as a clean lint run. **A zero count from a failed compile is not a pass**, and the only
thing that caught it was switching to `cargo nextest run --workspace`, whose output made the

Six `VlessConfig` literals across `xray-tui-db` (`database.rs`, `export.rs`, `models_toasty.rs`,

`fresh_open_creates_schema_and_sets_user_version_tag`, which pins the schema tag and was asserting

### What the full gate surfaced

- **The schema tag test hardcoded `13`** in three places. Rather than re-hardcode `14` (the same

- **All five long-standing `xray-tui-db` clippy errors are FIXED, not carried.** They were carried

## Post-gate correction (2026-10-01) — three defects the "complete" state was asserting away

A reviewer checking this plan's own claims against the tree found three things the final gate had
been reporting green while the code said otherwise. All three are now fixed, and two of them are
behaviour, not documentation.

### 1. T24 covered only half the batch kinds

`after_fast_settle` returned at `if !self.real_phase { return; }` **above** the quic arm, so a
**fast-ONLY** batch — the plain "Fast Ping" mode — never reached the exemption and kept the
TCP-derived `[fast]` marker. That is §8.1's symptom, on the mode a user is most likely to press.

The whole hard-failure arm now sits above that guard, and the guard moved below it. The expensive
part (`is_quic_plugin_link`, a config load) still lives on the rare hard-failure branch, so the
cost stays bounded by the hard-failure rate rather than by the plan size — §8.1 item 1's
constraint is preserved. The retraction is a statement about the FAST probe's verdict, not about
the real level, so it must not be gated on whether a real level exists.

`a_fast_only_batch_also_retracts_the_quic_rows_fast_marker` pins this, and **its non-vacuity was
proven**: moving the guard back above the arm makes it fail with the `[fast]` marker present.

### 2. The retraction destroyed a valid earlier marker

`retract_fast_marker` set `error = None`. But `after_fast_settle` holds the **plan-time snapshot**,
and the fast half only ever wrote into a clone — so `link.error` is whatever verdict the row
carried BEFORE this batch, possibly a valid `[real]` marker from an earlier run inside
`error_ttl_hours`. Blanking it threw that away, and a stop or queue-full retirement of the real
half afterwards left the row with no marker at all.

It now re-stages the snapshot **verbatim** — which is what withdraws the fast half's staged
verdict, because `stage` REPLACES the pending entry per (link, group). Same shape as every other
patch in this batch, which is built from the snapshot.

### 3. `dial` had no refusal gate (found by making row 8's test honest)

Row 8's test `continue`d past every refused row, so it never called `dial` on them and proved
nothing about the wire. Removing the `continue` failed `left: 4, right: 1` and exposed a real hole:
`outbound::dial` opens a socket for any config it is handed. The production gate
(`resolve_runtime_core`) covers the app path, but `dial` is what the in-process SOCKS5/HTTP inbound
calls, so an inbound built from a refused row — `mode=quic`, whose server answers on UDP — opened a
**TCP connection** and failed in the framing layer. Decision 20's failure mode.

`ProxyOutbound` now carries the row's `kind` (it lives on the `Protocol` ROW, not on the typed
config), and `dial` asks the same `capability` the app asks before opening anything. Non-vacuity
proven by removing the gate and reproducing `left: 4`.

- **`transport/v2ray/mod.rs` promised an arm that does not exist.** Its doc said quic "is the

### A design decision a reviewer pushed back on, and why it stands

The row-8 fix put the refusal gate inside `outbound::dial`. A reviewer argued this is wrong —
that `dial` "dials whatever it is handed", that enforcement belongs in the caller
(`resolve_runtime_core`), and that the original test's `continue` existed for that reason.

Both halves of that are accurate about the code **as it was**. The argument was weighed against
the code as it now stands, and the gate stays, for four reasons:

1. **It closes a surface, not just a test.** `resolve_runtime_core` is the *app's* decision point.
   `dial` is what the in-process SOCKS5/HTTP inbound calls, and it is handed a `ProxyOutbound`
   straight from `ServerConfig`. Nothing on that path consults `capability` today. A refused row
   configured there opened a TCP connection to a server answering on UDP — decision 20's failure
   mode, reachable from the crate's own public config surface.
2. **The kind is carried, not derived.** The reviewer's sharper point was that `kind` is NOT
   derivable from the config variant: `proto_kind_for_method` (`ss.rs:296-299`) decides
   `Shadowsocks` vs `Shadowsocks2022` from the **method**, so a variant-only derivation would hand
   `support_reason` the wrong kind for a 2022 row. That is correct, and it is exactly why the
   change adds `kind: ProtocolKind` to `ProxyOutbound` and fills it from the `Protocol` **row**
   (`protocol.proto_kind`) — the same value the app gates on. No `proto_kind()` was added.
3. **The kind is carried because it is CONSEQUENTIAL — the reviewer's point, which my first
   draft of this note had backwards.** `capability.rs:119` matches
   `(ProtocolKind::Shadowsocks | ProtocolKind::Shadowsocks2022, ProtocolConfig::Ss(..))`, which
   only shares the *entry* into `ss_reason`. Inside it, `ss_reason` branches on the kind:
   `if method.kind() != kind { return Some("shadowsocks method family does not match the
   protocol kind") }` (`capability.rs:415`), and `SsMethod::kind()` (`protocol/ss/method.rs:62-67`)
   derives `Shadowsocks` vs `Shadowsocks2022` from the **method family**. So the two SS kinds DO
   diverge, and a gate handed the wrong one would refuse a perfectly valid row — a 2022 kind on a
   classic `aes-128-gcm` config is refused, and that is already pinned at `capability.rs:1399-1402`.

   The implementation is right *because* the kind comes from the `Protocol` row
   (`protocol.proto_kind`), which is the same value the app gates on and the same one
   `proto_kind_for_method` derived when the row was written. Passing it in is not a formality: it
   is the only way this gate is safe.
4. **It is one pure call over a config already in hand**: no load, no allocation, no second
   source of truth. It asks the same `capability` the app already asks, one layer earlier.

What the row's wording now says: enforcement exists at BOTH seams, and this test pins the one
that was missing.

### A test that did not test what its name claimed

`the_outbound_kind_is_what_the_gate_actually_reads` was added to pin the *wiring* of
`ProxyOutbound::kind` into the gate — and its body constructed no `ProxyOutbound` and called no
`dial`. It was three direct `capability::support_reason` calls, which is precisely what
`capability.rs:1392` (`ss_kind_and_method_family_must_agree`) already asserts. It re-ran an
existing test at a second address while its name promised the field wiring was pinned. It was not.

Rewritten to drive `dial` at accept-and-record listeners: the mismatched kind must be refused by
the family's own rule and open **no** socket; the matching kind must get all the way to connecting
— otherwise the mismatch half would pass for the wrong reason. **Non-vacuity proven:** substituting
a variant-derived kind for the field (the exact bug the field exists to prevent) makes the
mismatch case go unrefused, and the test fails.

Its first run also caught a bug in itself: the accepted-connection counter was shared across both
iterations, so the refused case read the earlier connection as its own. Reset per iteration.

The generalisable failure, now the third instance of its kind in this plan: **a test's name is a
claim about coverage, and nothing verifies the name** — the same shape as a plan sentence claiming
an edit landed. Both were caught by checking the assertion against the cited requirement, not by
the suite being green.
